# Переход с MCTGAuth 0.6.4 на 0.6.5

[English version](MIGRATION_0.6.4_TO_0.6.5.md)

Требуется согласованное обновление backend, сервера и клиента. Протокол 2 требует поддержку fingerprint, поэтому клиент 0.6.4 не сможет войти на сервер 0.6.5.

1. Создайте резервные копии SQLite и Minecraft-кэша `mctgauth/accounts.json`.
2. Создайте новый случайный секрет не короче 32 символов и задайте `DEVICE_FINGERPRINT_SECRET` только в окружении backend. Не переиспользуйте `AUTH_API_TOKEN`, не коммитьте значение и не копируйте его на Minecraft-сервер или клиент.
3. При необходимости настройте `DEVICE_FINGERPRINT_ENABLED`, `DEVICE_OBSERVATION_RETENTION_DAYS`, `DEVICE_BAN_ENABLED` и `DEVICE_SIGNAL_WEIGHT_<SIGNAL>`. По умолчанию сильные сигналы включены, сбор GPU/MAC на клиенте выключен, документированный срок хранения — 365 дней, явные device-ban включены.
4. Разверните `auth-backend-0.6.5.tar.gz`. При старте транзакционно применяется `V008__device_fingerprints_and_bans.sql`; существующие пользователи, аккаунты, заявки и аудит сохраняются.
5. Проверьте `/health` и `/version`: приложение `0.6.5`, схема `8`.
6. Остановите Minecraft, установите `mctgauth-server-0.6.5.jar`, затем раздайте всем игрокам `mctgauth-client-0.6.5.jar` до открытия сервера.
7. Проверьте обычный вход, вход известного кэшированного аккаунта без backend и интерфейсы устройств/блокировок модератора. Не создавайте настоящую production-блокировку только для проверки деплоя.

Minecraft-кэш мигрирует со схемы 1 на 2 на месте. Полный reset удаляет наблюдения устройств, связи, блокировки, эффекты и исключения, создаёт пустой кэш schema 2 и сохраняет миграции БД и права модераторов.

Откат бинарных файлов не откатывает SQLite schema 8. Восстановление резервной копии выполняйте только как явную согласованную recovery-операцию.
